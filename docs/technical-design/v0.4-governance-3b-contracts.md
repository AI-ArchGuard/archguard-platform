- 状态：3B contract freeze；API 尚未在运行时提供
- 阶段：`v0.4.0-governance` / 3B
- Issue：[archguard-platform#19](https://github.com/AI-ArchGuard/archguard-platform/issues/19)
- 机器契约：[governance-v1.json](../../openapi/governance-v1.json)
- 固定消费方证据：[Samples 指纹向量](https://github.com/AI-ArchGuard/archguard-samples/tree/main/governance)

## 边界和兼容线

本契约扩展现有 Platform REST `/api/v1`，并不改变已发布 Scanner Result Schema `0.1.0` 或现有 Platform v1 端点。3C–3E 逐步实现基线、门禁和 GitHub 入口；3B 只冻结消费者可依赖的字段、算法及失败语义。Git Provider 在领域中用 `provider` 与外部仓库 ID 表示，阶段 3 只接受 `github`。Platform 不接收 Git 凭据、源码或源码归档，也不 clone/fetch。

一个报告提交唯一绑定 URL 中的 `projectId` 和 `repositoryId`、不可变 `ruleSetVersionId`、`GitRevision`（commit SHA、目标分支）、可选 `PullRequestRef`、Scanner/Result Schema 版本及原始报告字节。Git commit SHA 为 40 或 64 位小写十六进制；目标分支为不带 `refs/heads/` 的 Git 分支名，使用 NFC，禁止控制字符、前后空白及空值。`PullRequestRef.headSha` 必须等于 `GitRevision.commitSha`。GitHub 外部仓库 ID 是稳定身份；`owner/name` 只用于展示。Repository、RuleSetVersion、Git 外部身份和报告中的 `project.identity` 必须属于同一 Project/Repository，任何不一致都失败关闭。

CI 的 commit、PR 和目标分支元数据是经过认证的提交者断言，单靠报告提交不能证明 Git ancestry，也不能更新当前 PR 状态。3E 的已验证 Webhook 保存 PR 最新 head SHA；只有与之相等的已持久化门禁才能发布为当前 GitHub 状态。迟到报告可保存审计，但不能覆盖最新状态。

## 报告提交与幂等

`POST /api/v1/projects/{projectId}/repositories/{repositoryId}/report-submissions` 使用 `multipart/form-data` 的 `metadata` JSON 部分和 `report` 原始 UTF-8 JSON 字节部分。报告最大 50 MiB，必须按发布的 Scanner `0.1.0` Schema 和引用闭合规则验证。先校验认证和 Project 边界，再校验大小、摘要、Schema、归属和 Git 元数据；错误不得回显报告正文或凭据。

客户端发送 `Idempotency-Key`（Project 范围内唯一，1–128 个可打印 ASCII 字符）。`reportSha256` 是原始报告字节的 SHA-256 小写十六进制。`requestDigest` 为以下有序 UTF-8 字符串的 SHA-256；每个字段必须拒绝 CR/LF，空的可选值用空字符串：

```text
archguard-report-submission-v1
projectId
repositoryId
ruleSetVersionId
provider
providerRepositoryId
commitSha
targetBranch
pullRequestExternalId
pullRequestHeadSha
pullRequestBaseSha
scannerVersion
schemaVersion
reportSha256
```

UUID 用小写标准形式，SHA 用小写形式，字符串在哈希前 NFC 规范化；最后一行后有且只有一个 LF。相同 Project、幂等键和请求摘要返回同一 `submissionId`，不创建第二份 ScanJob、Finding 或 GateEvaluation；同键不同摘要返回 `409`。同一 Project 中不同键但相同请求摘要也返回原提交。不同 Project 的键与摘要不能互相命中。首次接受返回 `202`，重放返回 `200`，响应实体相同。`submission.status` 是处理生命周期，不扩展门禁结果枚举。

认证主体必须有该 Project 的提交权限；路径中的 Project/Repository 不可通过请求体覆盖。跨 Project 或不可见资源返回隐藏式 `404`。`429/5xx` 允许客户端以同一幂等键重试；非成功响应不得留下半份可见业务结果。报告验收和门禁求值是分开的持久化步骤，后续状态可轮询。

## Platform Finding 指纹 `platform-finding-v1`

Platform 从已验证的 Scanner 报告计算逻辑指纹。`finding.id`、`finding.fingerprint`、`subjectId`、Evidence ID 只作为同一报告内的引用；不直接作为跨扫描哈希输入。指纹载荷为 `projectIdentity`、`ruleId`、`ruleVersion`、`subject` 和 `discriminator` 五个 JSON 字段。所有字符串 NFC；JSON 对象键按 Unicode 码点升序，数组保留契约指定顺序，UTF-8 编码，不转义非 ASCII 字符，不插入空白。指纹为 `SHA-256(UTF8("archguard-finding-v1\n" + canonicalJson))`，64 位小写十六进制。基线比较空间另按 `Project + Repository + targetBranch + RuleSetVersion` 隔离；算法版本和规范载荷摘要必须随结果保存。

实体规范身份如下；所有字段都来自已闭合校验的 `0.1.0` 报告：

| Finding 类型 | `subject` 规范身份 | `discriminator` |
|---|---|---|
| 依赖规则：forbidden-component、illegal-package-dependency、internal-module-access、layered-architecture、controller-repository-access | `edge`：dependency.kind、source/target 的组件规范身份 | 唯一 `archguard.violation` |
| 复杂度规则 | `component` 或 `artifact` 规范身份 | 唯一 `archguard.metric`；排除当前 metric.value 和 threshold |
| 必需注解规则 | `component` 规范身份 | 唯一 `archguard.required-annotation` |
| 依赖环规则 | `cycle`：唯一 `archguard.graph-scope` 与按规范 JSON 升序排序的环顶点组件身份 | 空对象 |

Artifact 身份由 `kind`、`language`、`repositoryPath`、`qualifiedName` 构成。Component 身份由父 Artifact 身份、`kind`、`language`、`qualifiedName` 构成；Component 的源码位置不参与。普通依赖身份由 `kind` 和有向 source/target Component 身份构成。环的顶点集合从 `finding.evidenceIds` 反查 Evidence ID 集合被完全包含的 dependencies；其 Evidence 并集必须恰等于 Finding Evidence，`subjectId` 必须是该集合中的 dependency。无法唯一确定闭合环身份时返回 `ERROR`，不得退回行号或 Scanner ID。

指纹不包含严重性、消息、位置、数组顺序、Evidence 摘要、扫描时间、Scanner Finding ID/指纹或复杂度当前值。Rule、逻辑实体、违规类型、Metric key 或必需注解变化会产生新身份。相同哈希对应不同规范载荷，以及同一报告中两个不同 Finding 得到同一规范载荷，均为契约错误。未知 Rule/subject 形状必须失败关闭，并通过新版本契约评审后支持。

Samples 的三份固定报告覆盖 13 个架构违规、2 个环和 0 Finding 的正常项目；15 个固定输出及顺序、行号、展示、值、Rule 与实体扰动由 `scripts/verify_governance_contract.py` 验证。它证明现有 Schema 对当前八条 Rule 足够；Scanner 不参与 3B 修改或发布新 Schema。

## 门禁结果与 CI 映射

`GET /api/v1/projects/{projectId}/repositories/{repositoryId}/report-submissions/{submissionId}/gate-evaluation` 在求值未完成时返回 `202`，只返回提交状态；完成后返回不可变 `GateEvaluation`。结果仅为 `PASS`、`FAIL`、`ERROR`。结果绑定候选提交、确切基线版本、RuleSetVersion、策略版本、指纹算法版本、GitRevision、三类计数、命中例外版本和求值时间。`ERROR` 可以没有基线版本，但必须包含稳定错误类别与代码；任何缺失基线、契约不兼容或指纹冲突都不能变成 `PASS`。

默认策略只阻断未被有效例外覆盖的 `NEW` high/critical。`EXISTING` 默认不阻断。CI 将 `PASS` 映射 `0`、`FAIL` 映射 `2`、`ERROR` 且 `errorKind=CONFIGURATION` 映射 `64`、其他 `ERROR` 映射 `70`。本地参数/认证配置错误在提交前退出 `64`；网络、报告契约和执行错误退出 `70`。Scanner 自身的退出 `2` 只表示它已写出违规报告，CI 仍须提交报告并使用 Platform 最终门禁作为治理退出码。

## 版本、权限与回滚

`platform-finding-v1` 和 `archguard-report-submission-v1` 是独立版本；任何规范载荷或摘要输入变更都升级版本，旧历史不重写。3C 消费指纹与基线，3D 实现门禁与例外，3E 接入 GitHub/CI，3F 再消费 Web 展示。回滚按 Web/CI Adapter → Platform 应用顺序停止新入口，保留不可变历史；未发布的 3B 契约可以整体撤回。当前不新增依赖、数据库迁移或运行时 API。

# 3D Technical Design：质量门禁与有期限例外

- 范围：Platform；对应 [Issue #21](https://github.com/AI-ArchGuard/archguard-platform/issues/21)。
- 前置：3C 合并且 Platform `main` CI 成功。
- 运行时接口：[质量门禁与例外 OpenAPI](../../openapi/governance-gates-v1.json)。3B 的报告提交/CI 门禁契约 `governance-v1.json` 仍待 3E 接通。

## 决策与边界

3D 不运行 Scanner，不接受源码或 Git 凭据，也不更改 Scanner Schema。输入为现有成功 ScanJob 与 3C 不可变比较。Maintainer 在 `Project + Repository + targetBranch + RuleSetVersion` 空间发起门禁评估。缺少基线返回持久化 `ERROR/64`，执行或指纹契约错误返回 `ERROR/70`；仅未被例外覆盖的 `NEW` `high`/`critical` Finding 触发 `FAIL/2`，其余为 `PASS/0`。`EXISTING` 与 `RESOLVED` 默认不阻断。结果同时记录具体 Comparison/Baseline 版本、策略版本、指纹版本、分类数量、阻断数量和匹配的例外版本。

`PolicyException` 是独立治理对象，不修改 ScanJob、Comparison、Baseline 或历史 Gate。它由 Maintainer 创建，明确限定单个逻辑指纹或 Rule ID、Project、Repository、分支和 RuleSetVersion，并记录原因、创建者、生效与到期时间。例外在 `[effectiveAt, expiresAt)` 内有效；撤销通过不可变新版本记录。过期仅由读取和评估时的服务器时间推导，不修改历史行。首版最长有效期 30 天，创建时到期必须在未来。Viewer 可读，Maintainer 可创建/撤销。未来如需更宽的审批规则，另行版本化策略，而非放宽此实现。

## 幂等、事务与审计

门禁请求使用 Project 内唯一 `Idempotency-Key`。服务端对 Project、Repository、分支、RuleSetVersion 和候选 Job 计算请求摘要；相同键与相同输入返回已封存结果，即使基线或例外随后改变；相同键与不同输入返回 `409`。要重新评估必须使用新键。发起时先鉴权并验证资源归属；跨 Project 不得读取、创建或撤销例外，也不得提交或读取门禁。

Flyway V4 新建只追加例外、撤销、门禁和命中表。数据库触发器禁止修改或删除历史记录，并禁止在封存门禁后追加命中。门禁结果及命中在一个事务写入、封存并审计。计算与写入拆开，避免 3C 比较事务失败时导致 `ERROR` 结果也被回滚。例外创建、撤销及门禁评估均有包含 actor、Project、traceId 和目标的审计事件；不记录报告正文和凭据。

## 兼容与验证

部署顺序：3C 运行时 → V4 迁移 → 3D 应用 → 后续 3E CI 报告提交。3D API 独立于冻结的 3B `governance-v1.json`，3E 将其接入 GitHub 最新提交与 CI 退出码。回滚时先停止 3E 消费，再退回 3D 应用；保留 V4 和不可变历史，不回改已发布迁移。

验证覆盖 NEW/EXISTING/RESOLVED 与严重性、输入顺序、有效/待生效/到期/撤销例外、重复键、历史不变、无基线 `ERROR/64`、跨 Project 失败关闭、空库及 V2/V3 升级。PR 和合并后 `main` CI 必须通过含 PostgreSQL 的完整验证；本地无 Docker 时不把单元测试误报为集成通过。3D 不代表 3E Webhook/CI 闭环已完成。

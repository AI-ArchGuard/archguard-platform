# 3G：治理闭环安全与恢复加固

本切片保持 Scanner Result Schema `0.1.0`、Finding 指纹 `platform-finding-v1` 和现有治理 API 不变。Platform 仍不持有 Git 凭据或 clone 源码。3G 跨仓库顺序为 Samples 固定报告证据、Platform 安全与审计、Deploy CI 重试；Web 继续消费 3F 只读接口。

Platform 在持久化治理写入成功事实之外，对进入 MVC 的治理写入拒绝或失败追加 `governance.write.reject` 审计。Flyway V6 在原有结果约束上增加 `FAILURE`，不改写 V1–V5。`401/403/404` 记 `DENIED`，`409` 记 `CONFLICT`，其余失败记 `FAILURE`。元数据仅有路由模板、HTTP 方法和状态码，另有 actor、Project、traceId；没有请求体、报告、Webhook Secret 或 Token。未通过身份层、未进入 MVC 的请求不在这条治理写入审计内，需由边界访问日志或身份系统记录。非法 JSON 报告明确返回 `422`，不产生扫描任务。

现有集成测试覆盖签名错误、Webhook delivery 重放与碰撞、乱序和迟到 head、跨 Project 读写、重复报告不重复产生任务与门禁、不可变基线、例外和 CI `FAIL/2`→`PASS/0`。3G 额外验证失败审计、V2–V5 到 V6 迁移及敏感信息不入审计。CI 重试只针对临时网络和指定 HTTP 状态；报告提交沿用确定的幂等键。GitHub Status 发布是至少一次尝试：响应丢失时同值状态可能重复，不能误称恰好一次。

发布顺序：先合并 Samples 固定证据，再部署 Platform V6 并确认其 `main` CI，最后启用新 Deploy 模板。回滚顺序相反：停用/回退 Deploy 模板，再回退 Platform 应用；V6 和既有审计事实保留，不执行 down migration。旧 Platform 不识别 `FAILURE` 的 Java 枚举，但数据库新增值不会影响其既有 `SUCCESS`、`DENIED`、`CONFLICT` 写入。最终 Compose 和真实公网 Webhook 验收属于 3H，不能把本地 MockMvc 或 Testcontainers 模拟当成真实投递。
